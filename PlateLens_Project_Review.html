PlateLens — License Plate Recognition Project Review

A self-hosted license-plate dataset review, model training, and recognition workspace.
Repository: https://github.com/myhoaki/plate-recognition-demo
Prepared for a beginner learning AI-based license plate recognition. Grounded in the actual source code — nothing is hypothetical unless explicitly labeled.

1. Executive Summary

PlateLens is a four-section web workspace for license-plate recognition:

  • Verify Datasets — review registered images, draw and adjust license-plate boxes, correct OCR text, set a review state, and save.
  • Train Detection — train a YOLO detector to localize license plates using verified, frozen dataset snapshots.
  • Train OCR — train a small CRNN to read characters from plate crops using verified OCR snapshots.
  • Recognition / Test — upload one vehicle image, run detector + OCR together, view boxes, crops, confidence values, and elapsed time; also run batch evaluation against a frozen test split.

Two applications exist in the repository, but only one is served by Docker Compose:

  • app.py (root) — a legacy Flask app. NOT served by Docker Compose. Stores labels as JSON files in docker/labels/.
  • backend/app/main.py — the FastAPI app that Docker Compose runs (uvicorn app.main:app). Stores metadata in PostgreSQL, images on disk, and runs long jobs via Celery + Redis.

This review focuses on the FastAPI backend, because that is what docker compose up starts.

2. Architecture

Components and how they communicate:

  • Browser (React/Vite frontend) — App.tsx, RecognitionTest.tsx, OCRDatasetReview.tsx. Calls the backend via HTTP fetch (JSON). Polls every 1–2 seconds for job status; no WebSockets.
  • Backend API (FastAPI, uvicorn) — backend/app/main.py exposes all REST endpoints. Delegates inference to alpr.py, training to training.py / ocr_training.py, evaluation to evaluation.py, and dataset management to datasets.py / dataset_registry.py.
  • PostgreSQL database — holds ImageRecord, Annotation, TrainingJob, EvaluationJob, DatasetSnapshot, DatasetSplitAssignment, DatasetManifest, DatasetProvenance, DetectionJob.
  • File storage (bind-mounted host folders) — datasets/raw/ (registered images), datasets/snapshots/ (frozen read-only snapshots), datasets/manifests/ (versioned JSON), docker/storage/uploads/ (user uploads), docker/training/ (jobs, checkpoints, best.pt, active.pt), docker/models/ (FastALPR model cache).
  • YOLO detector — TrainedYoloDetector (ultralytics) or FastALPR default yolo-v9-t-384-license-plate-end2end. Outputs bounding boxes in pixel coordinates plus detection confidence.
  • OCR recognizer — FastALPR default cct-xs-v2-global-model, or custom CRNN (PlateOCRNetwork) trained via CTC loss. Reads plate crops and returns text + confidence.
  • Background worker (Celery + Redis) — one worker with concurrency=1. Runs detection jobs, training jobs, and evaluation jobs asynchronously. Redis is both broker and result backend.

Data flow: Browser HTTP → FastAPI → PostgreSQL (metadata) + disk (files). FastAPI enqueues long jobs to Celery → Redis → worker. Worker reads/writes PostgreSQL and disk. Models load weights from docker/models/ or docker/training/ and cache them in memory via lru_cache.

3. End-to-End Workflow: One Image

Tracing a hypothetical image car001.jpg (1920×1080) through the Recognition / Test path. Every file/function reference is real code.

Step 1 — Image upload

Frontend: RecognitionTest.tsx:51–57. User picks a file, clicks Run recognition. Browser POSTs to POST /api/images/upload.

Backend (main.py:558–586): save_upload() (storage.py:48) streams the file in 1 MB chunks to docker/storage/uploads/<uuid><ext>, computes SHA-256, enforces the 15 MB limit, and decodes dimensions with OpenCV. An ImageRecord row is inserted into PostgreSQL (id, source=upload, sha256, storage_key, width, height). Duplicate SHA-256 returns the existing record.

Failure: wrong file type → 400; >15 MB → 413; unreadable image → 400.

Step 2 — Run recognition (detector + OCR together)

Frontend: RecognitionTest.tsx:53. POST /api/recognition with {image_id, detector_job_id, ocr_job_id}.

Backend (main.py:87–136): loads the ImageRecord, resolves the file path via image_path() (storage.py:68), resolves checkpoints (validates completed TrainingJob and model file under docker/training/jobs/<id>/, otherwise uses active checkpoint docker/training/active.pt / active_ocr.pt, otherwise FastALPR defaults in alpr.py:87–97), then calls run_detection(path, detector, ocr) (alpr.py:108).

Each plate crop is base64-encoded into crop_data_url (main.py:124–133) so the frontend can show crops without another request. Returns detections plus elapsed_ms.

Step 3 — YOLO detection

Backend (alpr.py:108–126, alpr.py:32–61): run_detection() calls get_alpr(...).predict(image). get_alpr() builds fast_alpr.ALPR with either default models (detector_model=yolo-v9-t-384-license-plate-end2end, ocr_model=cct-xs-v2-global-model, ocr_device=cpu) or trained models (TrainedYoloDetector + TrainedPlateOCR). TrainedYoloDetector.predict() (alpr.py:39–61) runs model.predict(frame) and returns DetectionResult objects with label=license_plate, confidence, and BoundingBox(x1,y1,x2,y2) in pixels.

Bounding-box meaning: (x1, y1) = top-left corner, (x2, y2) = bottom-right corner, in pixel coordinates of the original image. Example: [420, 540, 560, 620] = a plate from x=420 to x=560, y=540 to y=620 (140×80 pixels).

Detection confidence = YOLO's objectness/class confidence that this box contains a license plate (0–1). Higher = more likely a plate is present. It does NOT mean the text is correct.

Step 4 — Plate crop

Backend (main.py:124–133): OpenCV crops frame[y1:y2, x1:x2] (NumPy slice) for each detection, re-encodes as JPEG, base64-encodes into crop_data_url. No separate cropping model — pure image slice using the detector's pixel box.

Step 5 — OCR recognition

Backend (alpr.py:108–126): FastALPR runs OCR inside each detected box. Default FastALPR OCR returns text + confidence from library internals. Trained OCR checkpoint uses TrainedPlateOCR.predict() (ocr_model.py:64–79): prepare_plate_crop() (ocr_model.py:39–45) converts to grayscale, resizes to 160×48, normalizes to 0..1, shape (1,1,48,160); forward pass through PlateOCRNetwork (ocr_model.py:17–33) — CNN → 2-layer bidirectional LSTM → linear over 37 classes (36 alphanumeric + CTC blank); decode_greedy() (ocr_model.py:48–61) — greedy CTC decoding, remove repeats/blanks, average per-character probabilities as confidence.

Alphabet: 0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZ. Unsupported text is preserved but cannot be used by the CRNN trainer until the alphabet is extended.

Step 6 — Final prediction

Backend (main.py:134–136) returns JSON with image_id, filename, width, height, file_url, detections (each with bbox_xyxy_pixels, text, ocr_confidence, detection_confidence, country, country_confidence, crop_data_url), elapsed_ms, detector_job_id, ocr_job_id.

Step 7 — Database / storage

Image file and metadata are stored in Step 1. Recognition results are NOT saved to PostgreSQL in this path — returned to the browser only. (Detection jobs via /api/detection-jobs do save annotations to the DB.) No automatic ground-truth comparison happens during inference.

Step 8 — Evaluation against ground truth (separate, not automatic)

Only if the user explicitly clicks Evaluate test split (RecognitionTest.tsx:61–69 → POST /api/evaluations, main.py:458 → run_evaluation_job, evaluation.py:64). Loads a frozen detector snapshot test split, runs run_detection() on each test image, matches predictions to ground truth using greedy one-to-one IoU ≥ 0.50 (evaluation.py:129–131). Text is trimmed and case-insensitive. Computes detection precision/recall, mAP50/mAP50–95, OCR exact accuracy, CER, and end-to-end accuracy (all plates match AND zero false detections AND zero missed plates). Stores results in EvaluationJob.results.

Failure scenarios

  • No plate detected: detections is empty. UI shows No plates detected.
  • Multiple plates: each detection returned independently with its own box and text.
  • OCR fails / empty: text is "", ocr_confidence is None. UI shows No text recognized.
  • Image unreadable: run_detection raises ValueError → API returns 422 Recognition failed.
  • Background job fails: Celery task sets status=failed and stores error (truncated to 2000 chars) in PostgreSQL (tasks.py:120–127, training.py:411–412, evaluation.py:176–177).
  • Checkpoint missing: selected_checkpoint() (main.py:96–109) returns 400 if job not completed or file missing.

4. YOLO and OCR in This Implementation

Object detection vs OCR

Object detection (YOLO) answers where is the plate? Outputs bounding boxes in pixel coordinates plus detection confidence. Class is always license_plate (class 0). OCR answers what does the plate say? Receives a cropped plate image, outputs text string plus confidence.

Default models (confirmed in code)

  • Detector: yolo-v9-t-384-license-plate-end2end — FastALPR-packaged YOLOv9 (app.py:39, alpr.py:80). Downloaded automatically on first use into docker/models/.
  • OCR: cct-xs-v2-global-model — FastALPR OCR (app.py:41, alpr.py:82). Runs on CPU (ocr_device=cpu).

Trained models (confirmed in code)

  • Detector training (training.py) uses ultralytics YOLO (training.py:231) starting from yolo11n.pt (training.py:249) or retained best_detector.pt (training.py:248). Trains to localize license_plate boxes. Output: best.pt → docker/training/jobs/<id>/best.pt and docker/training/best_detector.pt.
  • OCR training (ocr_training.py) trains custom CRNN PlateOCRNetwork (ocr_model.py:17–33) with CTC loss (nn.CTCLoss, ocr_training.py:490). Output: best.pt with state_dict + alphabet.

Does YOLO training change the OCR model?

No. Confirmed in code. Detector training only touches YOLO weights (best_detector.pt, active.pt). OCR training only touches CRNN weights (best_ocr.pt, active_ocr.pt). run_training_job dispatches to run_ocr_training only when config.model_type == "ocr" (training.py:212–216).

CPU vs GPU (confirmed in code)

  • Default FastALPR inference uses ocr_device=cpu (app.py:41, alpr.py:83).
  • YOLO training: device=None if auto, else config device (training.py:348) — Ultralytics picks CUDA if available.
  • OCR training: torch.device("cuda" if torch.cuda.is_available() else "cpu") (ocr_training.py:475).
  • Docker Compose does not request GPUs, so without Docker GPU support training runs on CPU and will be slow.

5. Annotation and Ground-Truth Workflow

How annotations are stored (confirmed in code)

PostgreSQL table annotations (models.py:33–50): bbox_xyxy_pixels (JSONB pixel box [x1,y1,x2,y2]), bbox_normalized_xywh (JSONB normalized [center_x, center_y, width, height] in 0..1), ai_detection (boolean), ai_result (AI OCR guess), verified_result (human-verified plate text / ground truth), detection_confidence, ocr_confidence, country, country_confidence.

How ground truth is created (confirmed in code)

  • AI pre-labels: detect_plates_for_labeling() (app.py:333–385, legacy Flask) or batch detection (tasks.py:14–127, FastAPI) runs detector, stores AI boxes with ai_detection=True, ai_result=OCR guess, verified_result=NULL.
  • Human corrects: in Verify Datasets UI (App.tsx:434–455, setText), user edits verified_result (typed uppercase) and can move/resize boxes. save() (App.tsx:397–411) POSTs to POST /api/images/{id}/annotations (main.py:655–713).
  • Save logic: save_annotations() (main.py:655) matches each manual box to an AI box by IoU ≥ 0.5; if matched inherits ai_detection=True, ai_result, confidences; otherwise ai_detection=False. Replaces all annotations for the image and sets review_status=needs_review, verified_at=NULL.
  • Verification: set_image_review_status() (main.py:632–640) sets review_status and verified_at (only when status=verified). Verified + verified_at not null is what makes an image eligible for training.

Key rule: OCR guesses are never saved as ground truth automatically. The human must type verified_result and set status to verified (README.md:17, app.py:496–500).

6. Dataset Splitting and Training Workflow

1. Which annotations qualify for training?

Detector: source=registered, review_status=verified, verified_at IS NOT NULL, at least one annotation (datasets.py:176–177, dataset_registry.py:176). OCR: annotations with non-empty verified_result, plus imported OCR CSV rows with verification_status=verified (ocr_training.py:246–282, dataset_registry.py:178–181).

2. Conversion to YOLO format

Each annotation's bbox_normalized_xywh = [center_x, center_y, width, height] in 0..1. Written as 0 <cx> <cy> <w> <h> (class 0 = license_plate) to labels/<split>/<sample_id>.txt (datasets.py:73–78, training.py:113–123). One class only: names: 0: license_plate in data.yaml (datasets.py:85).

3. Images and labels matched

By sample_id (= image id = UUID). Snapshot manifest lists each sample with image path, label path, split, SHA-256. Training links/copies the image and writes the matching .txt label file.

4. Train/validation/test splitting

Detector snapshots: create_manifest() (dataset_registry.py:138–249) assigns splits. Existing DatasetSplitAssignment rows preserved; new verified samples default to train; groups share a split. Deterministic 80/10/10 via initial_split() (dataset_registry.py:90–93, SHA-256 of group_id). Training from scratch: _split_sizes() (training.py:26–37) splits verified images 80/10/10 with random.Random(42).shuffle(). Reassigning a test sample requires --confirm-test-change (dataset_registry.py:263–266).

5. Training configuration

schemas.py:44–59: model_type (detector/ocr), dataset_snapshot_id, epochs (1–300), batch_size (1–64), image_size (320–1280), device (auto/cpu/0/1…), train_ratio/validation_ratio/test_ratio (must sum to 1).

6. Pretrained model and architecture

Detector: Ultralytics YOLO, weights yolo11n.pt (training.py:249) or retained best_detector.pt (training.py:248). OCR: PlateOCRNetwork (CNN + BiLSTM + linear, ocr_model.py:17–33), alphabet 0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZ (37 classes incl. blank), input 160×48 grayscale.

7. What happens in a single epoch (detector)

training.py:201–410: _prepare_dataset() builds/validates YOLO dataset dir and data.yaml. YOLO(...).train() with callbacks: on_train_batch_end (record_batch) updates current_batch/total_batches in DB every ~1% of batches; on_fit_epoch_end (record_epoch) reads YOLO metrics (mAP50, mAP50–95, precision, recall, losses), computes score = 0.1*mAP50 + 0.9*mAP50–95, calls _record_epoch_metrics() which saves epoch history and marks is_best if score is highest. If best, copies runs/detector/weights/best.pt to jobs/<id>/best.pt. Validation callbacks track val progress. After all epochs, runs model.val(split=test) on test split, collects test_metrics. Copies best.pt to jobs/<id>/best.pt and global best_detector.pt, marks job completed, sets model_path.

8. Where metrics and checkpoints are saved

Metrics: PostgreSQL TrainingJob.metrics (JSONB) — epoch_history (last 300 epochs), best_epoch, best_score, best_metrics, final test metrics. Exposed via GET /api/training-jobs/{id}. Checkpoints: docker/training/jobs/<id>/best.pt and global docker/training/best_detector.pt / best_ocr.pt.

9. Best checkpoint selection

Detector: is_best = score >= best_score where score = 0.1*mAP50 + 0.9*mAP50–95 (training.py:301–304). OCR: best = highest val_plate_accuracy (ocr_training.py:530). Epoch marked is_best in epoch_history corresponds to best.pt.

10. How trained model becomes available for inference

POST /api/training-jobs/{id}/activate (main.py:957–980) copies jobs/<id>/best.pt → docker/training/active.pt (detector) or active_ocr.pt (OCR). get_alpr() (alpr.py:87–97) prefers active.pt/active_ocr.pt if present, else falls back to FastALPR defaults. POST /api/recognition can also select a specific completed checkpoint by detector_job_id/ocr_job_id.

7. Model Evaluation and Deployment Workflow

Evaluation (confirmed in code)

  • Training-time validation/test (YOLO built-in): during detector training, Ultralytics validates on val split each epoch and tests on test split at the end (training.py:373–382). Metrics: mAP50, mAP50–95, precision, recall.
  • End-to-end batch evaluation (explicit, user-triggered): POST /api/evaluations → run_evaluation_job (evaluation.py:64). Runs detector+OCR on every image in frozen snapshot test split. Greedy one-to-one IoU ≥ 0.50 matching (evaluation.py:129–131). Text trimmed, case-insensitive (README.md:20). Metrics: detection precision/recall, mAP50/mAP50–95 (via Ultralytics), OCR exact accuracy, CER, end-to-end accuracy (all plates match AND zero false detections AND zero missed plates). Results stored in EvaluationJob.results; incorrect examples (up to 500) saved for inspection.

Deployment (confirmed in code)

No separate model registry or deployment pipeline. Deployment = activating a checkpoint: training completes → best.pt saved → user clicks Activate → active_training_model() copies to active.pt/active_ocr.pt → subsequent inference (get_alpr()) uses active checkpoint if present. A specific checkpoint can also be selected per-recognition request.

8. Current UI Problems and a Proposed Simpler UI

What the UI currently does (confirmed in code)

App.tsx is a single-page app with 4 sections switched by tabs: production (Verify Datasets), detector training, OCR training, recognition. RecognitionTest and OCRDatasetReview are child components. The production view mixes image review, snapshot creation, import, batch detection, metrics, and the Konva canvas editor in one long view. Training configs (epochs, batch size, image size, ratios) sit alongside split progress and metrics. Snapshot management (create/import/delete) is embedded in the production view, detached from training. No visual connection between verified annotation → snapshot → training run → activated model → inference result.

Why it may feel cluttered

  • One component (App.tsx, 690 lines) handles navigation, image polling, drawing, snapshots, training, metrics, keyboard shortcuts.
  • Snapshot create/import/delete controls are in Verify Datasets, but snapshots are consumed in Train Detection / Train OCR.
  • Confidence thresholds, review filters, and pagination are interwoven with the canvas editor.
  • Training metric names are raw Ultralytics keys (metrics/mAP50(B)) exposed directly to the user.

Proposed simpler structure (recommended — not implemented)

  • Explore — primary action: run recognition on one image. Shows original image, detection boxes, plate crops, recognized text, confidences, elapsed time. Checkpoint selection defaults to active model.
  • Label & Verify — primary action: correct boxes + plate text, set verified status. Shows image grid, canvas editor, per-plate AI guess vs verified text. Advanced: split ratios, manifest versioning, provenance hidden.
  • Train & Evaluate — primary action: train detector/OCR, compare checkpoints. Shows snapshot list, training progress (epoch, batch, val), metrics (mAP, accuracy, CER), evaluation results, activate model. Advanced: raw SQL, dataset imports, legacy paths hidden.

Each screen has one clear primary button; advanced options behind an Advanced toggle. This is a recommendation only — the current code does not implement this split.

10. Beginner Learning Roadmap with Practical Exercises

Phase 1 — Understand the running system (no code changes)

  • Run the stack: PUID=$(id -u) PGID=$(id -g) docker compose up -d --build. Open http://localhost:8000.
  • Walk the UI: Verify Datasets → sync datasets folder → draw a box → type plate text → Save → Verify. Observe AI boxes are orange; manual boxes are green.
  • Trace one API call: browser DevTools → Network tab. Watch payload of POST /api/recognition and its response (crop_data_url, detection_confidence, ocr_confidence).

Phase 2 — Read code while running

  • Set a concrete box → trace to DB: after saving an annotation, inspect PostgreSQL: images row → annotations row with bbox_xyxy_pixels and verified_result.
  • Read alpr.py:108–126 (run_detection): map each output field to its source (box.x1..y2, ocr.text, result.detection.confidence).
  • Read training.py:282–304 (record_epoch): understand where mAP50 comes from and how is_best is decided.

Phase 3 — Experiments (read-only, no destructive commands)

  • Compare confidences: run recognition on several images. Note cases where detection_confidence is high but ocr_confidence is low (or vice versa). This teaches detection confidence ≠ text correctness.
  • Read an evaluation result: queue Evaluate test split against a detector snapshot. Watch detection_precision, detection_recall, ocr_exact_accuracy, end_to_end_accuracy.
  • Read the snapshot manifest: open datasets/snapshots/detero/<id>/manifest.json (if any exist). Verify it contains split_counts, data.yaml reference, per-sample SHA-256.

Phase 4 — Safe changes (after you understand)

  • Rename a UI label (e.g., Verify Datasets → Label & Verify) in App.tsx:583.
  • Add a new metric display in the training status section using an existing key from trained.metrics.
  • Do NOT retrain models, modify database schema, or delete snapshots until you've traced a full training run end to end.

Concepts to master, in order

  • Bounding box (xyxy pixels vs normalized xywh) — logic.py:7, models.py:39–40.
  • IoU (overlap between two boxes) — logic.py:7, evaluation.py:125–126.
  • Confidence score (what it does and doesn't mean) — alpr.py:108–126.
  • Ground truth vs AI guess — models.py:42–43, main.py:696–698.
  • Train/val/test split and data leakage — dataset_registry.py:90–104, training.py:87–124.
  • Epoch / batch / loss / backprop — ocr_training.py:498–517 (CRNN, easier to read than YOLO internals).
  • mAP, precision, recall — training.py:301, evaluation.py:166–167.
  • Checkpoint and activation — main.py:957–980, training.py:394–396.
  • CPU vs GPU — ocr_training.py:474–479, training.py:348.
